# Loom 架构设计

> 本文描述 Loom 已实现的运行时架构,以及它背后的设计原则。
> 面向引擎 / UI 框架开发者。

## 1. 设计原则

- **P1 静态/动态显式分界**:编译期就知道「哪里会变」。静态部分零运行时构造;动态部分细粒度订阅。
- **P2 拒绝 archetype 搬迁**:运行期更新只改组件「值」,不插/删组件;频繁切换的状态用枚举 / 标志字段表达。
- **P3 关注点分离**:结构、响应、样式三层各自独立编写、测试、热重载。
- **P4 可预测优先于极致**:宁可牺牲一点理论峰值,也要让性能行为稳定可解释。
- **P5 渐进采用**:能与现有命令式代码共存,局部替换,不强制全量迁移。
- **P6 失败可见**:错误边界、校验、报错 span 映射,错误不静默。

## 2. 三层分离

```
┌──────────────────────────────────────────────────────────┐
│ 结构层 Structure(编译期 / 可解释)                           │
│   loom! 宏 / Element 构建器 → 数据层视图描述                  │
├──────────────────────────────────────────────────────────┤
│ 响应层 Reactivity(运行期,细粒度)                           │
│   Signal / Memo / Effect,无毛刺传播                         │
├──────────────────────────────────────────────────────────┤
│ 样式层 Style(资产,可热重载)                                │
│   token / class / 作用域 / 响应式断点 / 级联                 │
└──────────────────────────────────────────────────────────┘
            ↓ 全部落到 ↓
┌──────────────────────────────────────────────────────────┐
│ 保留树 Tree(分代 Arena + Keyed 协调器)                      │
│ 布局引擎(纯 Rust Flexbox) → 最小化 BackendOp 流 → 渲染后端  │
└──────────────────────────────────────────────────────────┘
```

每一层都是独立 crate,可单独使用,也可单独测试与演进。这是「易维护」的结构性保证:
改一层不动其它层。

## 3. 数据流

```
用户输入 / 事件
      │
      ▼
  Signal 更新 ──→ 标记依赖的 Memo / Effect 为脏(无毛刺调度)
      │
      ▼
  构建新的 Element 树(廉价、数据层、可每帧重建)
      │
      ▼
  Ui::update(&tree)  ← 核心协调步骤
      ├─ keyed 协调(LIS 最小化):复用能复用的节点,只对差异发出 BackendOp
      ├─ 种类变更(Box↔Text↔Custom)→ 局部重建
      └─ 其它字段差异 → SetText / SetPaint / Reorder 等最小操作
      ▼
  Ui::compute_layout(viewport)
      └─ 重算布局,仅对几何变化的节点发出 SetLayout
      ▼
  Backend::apply(ops)  → 渲染 / 无头记录
```

关键:**没有整树 diff**。协调器以保留树为基准,逐层做 keyed 比对,输出的
`BackendOp` 流严格正比于「实际变化」。

## 4. 核心契约:成本 ∝ 变化量

Loom 的全部性能设计都服从一个契约:

> **更新成本与「实际变化量」成正比,而非与「场景规模」成正比。**

落地机制(均为已实现部分):

| 机制 | 作用 | 对应 crate |
|---|---|---|
| 数据层 `Element` | 每帧重建视图描述是廉价的(无 ECS 写入) | `prism_ui` |
| LIS 最小化 keyed 协调 | 列表增删/重排按 key 复用节点,最小 move 次数 | `prism_ui_tree` |
| 字段级 BackendOp | 只发出 `SetText` / `SetPaint` / `Reorder` 等真实增量 | `prism_ui` |
| 布局几何差分 | `compute_layout` 只对坐标/尺寸变化的节点发 `SetLayout` | `prism_ui` + `prism_ui_layout` |
| 无毛刺响应传播 | Signal 变化只扰动真正依赖它的观察者,且值未变不传播 | `prism_ui_reactive` |
| 文本测量只用 ×÷ | 确定性测量,无超越函数依赖 | `prism_ui` |

**可验证性**:`RecordingBackend` 会记录每次 `update` / `compute_layout` 产生的
操作序列。测试直接断言「相同输入 → 零新增操作」「keyed 反转 → 0 新建 / 0 删除 /
1 次 reorder」,把性能契约变成可回归的事实,而非口号。

## 5. 协调器:为什么能避免 archetype 搬迁

保留树(`prism_ui_tree`)用 **分代 Arena** 存储节点,句柄是 `(index, generation)`,
删除后代次自增,避免 ABA 悬垂引用。协调器对子节点列表做 **keyed diff**:

- 产出 `Diff { ops: [Keep/Move/Create], removals }`;
- `Move` 的数量由 **最长递增子序列(LIS)** 求解最小化 —— 这与 React 的 keyed
  reconciliation 同源,但在 Rust 里做了零分配的紧凑实现;
- 能复用的节点 **只改字段**,不新建、不销毁。

当这套协调结果落到 ECS 时,对应的更新策略是「改组件值,不插删组件」,因此
不会触发 archetype 搬迁(BSN 的一个潜在成本点,见
[bsn-comparison.md](bsn-comparison.md))。

> 注:响应层到 ECS 实体字段的自动绑定目前仍是 **规划中**(见 roadmap)。当前
> 已交付的是「数据层 `Element` → 保留树 → BackendOp」这条完整、经测试的链路,
> 以及独立可用的响应、样式、布局、动画四层。

## 6. 后端抽象

渲染与引擎细节都被收敛到一个窄接口:

```rust
pub trait Backend {
    fn apply(&mut self, op: BackendOp);
}
```

`BackendOp` 覆盖 `Create / SetText / SetLayout / SetPaint / Remove / Reorder`。
`RecordingBackend` 是内置的无头参考实现,用于测试与快照;GPU / 平台渲染器只需
实现同一 trait 即可接入,视图代码无需改动。这既是「可测试性」的基础,也是
「跨引擎 / 跨后端」的解耦边界。
